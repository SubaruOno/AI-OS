## Purpose

The audit plugin covers pipeline stages 3-7, from the first discovery session through to the clickable prototype presented at conversion. It is the delivery engine of the Bosar consulting workflow: Agent 3 (Process Mapper) extracts structured process data from meeting transcripts fetched via the CRM into per-domain audit files; Agent 4 (Process Analyst) enriches that data with tool research, value calculations, and strategic approaches; Agent 5 (Generator) renders HTML deliverables from the enriched data; Agent 6 (Solution Architect) produces requirements specs, architecture docs, and clickable prototypes; Agent 7 (Feedback Reviewer) is the human QA layer — it ingests Loom review videos or typed feedback, maps corrections to specific audit data items, applies changes with cascading recalculations, and maintains a permanent audit trail of every review round. Bo runs each agent sequentially after each client session. **This distribution is standalone** — transcripts, emails, and documents are placed directly into each client's `01-materials/` folder and there is no CRM. The plugin *can* optionally connect to a CRM (Supabase via HTTP MCP) for transcript sync and task tracking when one is configured, but it never blocks on CRM failures and a missing CRM is skipped silently by design.

## Source of truth

`clients/{client-slug}/03-audit/data/` contains the canonical data contract for the entire audit pipeline. In v4 (current), audit data is split into per-domain files: `meta.json`, `extraction.json`, `findings.json`, `opportunities.json`, `strategy.json`, `architecture.json`, `reviews.json` (added 2026-05-13), with `audit-manifest.json` as the index. Each domain file is owned by one agent. HTML deliverables are derived outputs, generated from these files and must never be edited directly.

Review round source material (transcripts, videos, frames) lives in `clients/{client-slug}/03-audit/reviews/RR-{NNN}/` — separate from the audit domain files.

The `audit_status` field (in `meta.json` for v4, duplicated in `audit-manifest.json` for quick access) is the state machine that gates agent progression:
- `"in_progress"` -- extraction sessions ongoing; Generator can produce process-map, findings, waste, client-website
- `"process_map_complete"` -- all sessions done; unlocks Analyst EI -> RI -> SA -> BR -> VR chain and Generator GB/GW

CRM project and task IDs are stored in `meta.json` under `crm.project_id`. These are used for task status updates but the CRM is not canonical, local files are. CRM sync is best-effort and never blocks the pipeline.

`clients/clients.json` is the master registry mapping client slugs to emails, portal URLs, and CRM contact IDs.

## Data contract — audit data schema

**Canonical schema:** `references/audit-data-schema.md` — single source of truth for all field definitions, types, and agent ownership. Schema version: **4.0.0** (migrated 2026-05-12).

### v4 Multi-File Domain Split

As of 2026-05-12, audit data is split into **per-domain files** with a manifest index. Each agent reads/writes only its own domain file(s), eliminating context dilution.

```
clients/{slug}/03-audit/data/
├── audit-manifest.json       # index: version, checksums, timestamps
├── meta.json                 # ~2KB, always loaded
├── extraction.json           # processes, tools, sessions (Extractor)
├── findings.json             # pain points, waste, questions (Extractor)
├── opportunities.json        # proposed changes, ROI (Researcher)
├── strategy.json             # strategic approaches (Researcher)
├── architecture.json         # requirements, architecture (Designer)
└── ingestion-manifest.json   # unchanged
```

| Domain | File | Write owner | Contains |
|---|---|---|---|
| `meta` | `meta.json` | Extractor | client_slug, company_name, crm, contact, blended_hourly_rate, audit_status (~2KB) |
| `extraction` | `extraction.json` | Extractor | processes, decision_nodes, tools, staff_roster, business_metrics, sessions, client_context |
| `findings` | `findings.json` | Extractor | pain_points, optimisations, waste_items, contradictions, follow_up_questions, completeness_checklist |
| `opportunities` | `opportunities.json` | Researcher | proposed_changes, roi_items, risk_register |
| `strategy` | `strategy.json` | Researcher (SA) | strategic_approaches, transformation_blueprint |
| `architecture` | `architecture.json` | Designer | requirements_spec, architecture_doc, architecture_verification, cowork_demos, branding |

**Reading:** `Read clients/{slug}/03-audit/data/{domain}.json` directly. No offset/limit needed.

**Writing:** Write the domain file, then update `audit-manifest.json` (set `domains.{domain}.updated_at` and root `updated_at`). For Python scripts, use `save_domain(slug, domain, data)` from `audit_reader.py`.

**Backward compatibility:** `audit_reader.py` auto-detects v4 (manifest present), v3 (nested single file), or v2 (flat single file). All consumers call `load_all(slug)` and get the same flat dict regardless of version. `generate.py` and all other scripts work unchanged across all versions.

**Clients on v4:** `brightside-services`, `riverside-dental`. All others remain on v3/v2.

**Auto-regen hook:** Fires only on `audit-manifest.json` writes (single trigger per save cycle). Domain file writes alone do not trigger regen.

**Value dimensions on proposed_changes[].value:** time_saving, productivity_enhancement, risk_reduction, customer_experience, scalability. All optional; `combined_annual_value_aud` sums whatever is populated.

**v4 migration wiki:** `references/schema-v4/WIKI.md` — full migration status, design decisions, and reference files.

## Conventions & gotchas

- **Audit data is append-only by design.** Agents enrich domain files progressively, never delete fields another agent wrote. The CRM block lives in `meta.json` under `crm`.
- **v4 write paths: one file per domain.** For v4 clients, write to `clients/{slug}/03-audit/data/{domain}.json` directly, then update `audit-manifest.json`. For Python scripts, use `save_domain(slug, domain, data)` from `audit_reader.py`. Never write cross-domain (e.g., Researcher never writes to `extraction.json`, except RI writing `processes[].plugin_scope`).
- **`audit_status` gates the pipeline.** In v4, check `audit-manifest.json` root `audit_status` (duplicated from `meta.json`) for quick access. The Analyst refuses to run EI if `audit_status != "process_map_complete"`. Set this field manually when all sessions are done, or let the Process Mapper set it when the completeness checklist passes.
- **Hook on manifest writes.** The PostToolUse hook in `.claude/settings.json` fires when `audit-manifest.json` is written and triggers auto-regen of existing HTML deliverables. The plugin-level hook in `hooks/hooks.json` fires on any audit file write and prints an advisory reminder.
- **Generator never writes HTML directly.** The agent calls `generate.py`; the script writes all HTML. If a deliverable looks wrong, fix the script, not the agent prompt.
- **Partial generation is valid.** `generate.py` produces whatever data is available. You can generate a process-map after Session 1 without waste or solutions data.
- **CRM tasks follow a fixed sequence.** Each agent updates its task to "Done" and marks the next task "In Progress": EI → RI → SA → BR → VR → Generate Deliverables → RE → BA → VA → BP. If `crm.project_id` is null, all CRM updates are skipped silently.
- **Meeting folders are the source of truth for transcripts.** Fathom transcripts are fetched into `clients/{slug}/01-materials/meetings/{YYYY-MM-DD}-{title-slug}/transcript.txt`. The Mapper cross-references these folder names against `sessions[]` in audit-data.json to detect unprocessed inputs.
- **Solution Architect has two tracks.** Custom-build (RE → BA → VA → BP) requires `proposed_changes[].implementation` and `.value` to be populated (needs Analyst BR). Cowork demo track (BC) only needs `proposed_tools[]` from RI. Run whichever fits the client conversation.
- **Deliverable output path is always `clients/{slug}/03-audit/deliverables/`.** Deploy reads from there. Do not save deliverables elsewhere.
- **Close-page templates** live in `templates/` (three variants: default, discovery, urgency) — used by the Sales plugin's close agent before the audit starts; included here as shared resources.
- **Sidecar memory** for each agent lives at `${CLAUDE_PLUGIN_ROOT}/_memory/{skillName}-sidecar/`. Agent 4's sidecar is at `bmad-apg-process-analyst-sidecar/`, Agent 6's at `bmad-apg-solution-architect-sidecar/`. Check there for cross-session state.
- **`crm.contact_id` in `meta.json` is used for CRM sync** — `list_contact_meetings` and `list_contact_emails` use it to fetch data. If `crm.contact_id` is not set, SU looks it up via `search_contacts(query: company_name)` and stores it.

## Sub-agent context packet convention

Both the Extractor (SU) and Researcher (RI/BR) dispatch sub-agents with filtered context packets rather than passing full domain files. This is the primary scalability mechanism for large clients.

**Rules:**
1. **Cap packet size at ~10KB.** Truncate arrays that grow with client size (e.g., `existing_pain_point_summaries` capped at 30 entries, `existing_tool_names` capped to names only).
2. **Include only what the sub-agent needs.** RI packets contain one proposed_change + its linked pain points, affected steps, and waste items — nothing else from opportunities or extraction.
3. **Never pass a raw domain file to a sub-agent.** Even meta.json (~2KB) should be distilled to the handful of fields the sub-agent actually uses.
4. **All new agents must follow this pattern.** Any agent that dispatches sub-agents must explicitly build a filtered packet and document its max size.

This pattern keeps sub-agent context constant regardless of audit size (1 session vs 10 sessions, 16 changes vs 50 changes).
