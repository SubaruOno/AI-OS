# Plan: 野球記録・分析プラットフォーム

**Created:** 2026-09-28
**Status:** Draft
**Request:** 既存の試合入力・分析Excelを置き換え、iPad/iPhone/MacとWindowsのWebブラウザから同じ試合データを記録・分析できるソフトの全体計画を決める。
**Purpose:** 既存VBAの入力と分析を段階的に再現し、端末を選ばず試合記録を行い、同じデータから分析結果を確認・出力できるようにする。

---

## Overview

### What This Plan Accomplishes

Excel VBAに分かれている試合作成、プレイ入力、試合記録、個人・チーム分析を、ひとつのデータ基盤を使うソフトへ置き換える計画を定める。最初は既存の入力列と集計結果を保つことを優先し、その後に操作性、共有、帳票を整える。

### Why This Matters

試合中にiPadから入力し、後でMacやWindowsから確認・分析できる。VBAが動く端末やExcelの状態に左右されず、入力と分析の手順を継続できる。

## Current State

### Relevant Existing Structure

- `分析シート_修正版.xlsm` は1シートの表紙を入口とし、VBA 61モジュールを含む。個人・チーム成績、打球方向、投手投球図、配球、ケース別、得失点パターンなどを作る。
- `2020年PSS京滋大学野球 (自動保存済み).xlsm` は試合作成用テンプレート。非表示を含む6シートとVBA 24モジュールを含む。191列の試合記録、出場選手、UserFormによるプレイ入力・訂正を持つ。
- 入力ブックには投球・打者・走者・守備・打球・作戦などの記録が同じプレイ行に格納される。試合ファイル作成マクロがテンプレートから試合別ブックを作り、入力マクロが行を追加する。
- 現在の滋賀大対策ツールは試合Excelを読み、打者・投手対策やHTML、PowerPoint、PDFを生成する。処理の流れと定義は[滋賀大 対策資料づくり](../docs/shiga-taisaku.md)、直近の京都外大回の判断と未完了事項は[引き継ぎメモ](../private/shiga-kyogai-2026aki.md)にある。
- 選手・試合の内部データは非公開であり、AI-OSのGit管理対象に持ち込まない。

### Gaps or Problems Being Addressed

- ExcelデスクトップとVBAに強く依存し、iPadやWindowsブラウザから同じ入力手順を使えない。
- 入力データの191列は人が直接扱いにくく、項目の意味や状態遷移が画面コードに埋まっている。
- 分析結果が多数のマクロとシート生成に分散し、計算ロジック・表示・保存が分離されていない。
- 現行ファイルには古い形式、過去のマクロ依存、修正時の取り違えがあるため、全機能を一度に置換すると照合が難しい。

## Proposed Changes

### Summary of Changes

- 2ブックの全入力項目、操作、帳票、計算式を棚卸しし、正式な機能カタログとデータ辞書を作る。
- iOS/iPadOSとmacOSではSwiftUIアプリ、WindowsではブラウザWebアプリを提供する。UIを各環境に合わせ、同一API・同一データモデル・同一計算ロジックに接続する。

- MVPでは試合作成、メンバー登録、ライブ入力、訂正、試合の保存・再開、主要な個人/チーム基本成績、Excel出力を作る。

- 認証、権限、バックアップ、監査ログ、端末別の操作設計を初期から含める。

## Design Decisions

### Key Decisions Made

1. **複数OSで同じデータと機能を使う:** ネイティブAppleアプリとブラウザWebアプリを、共通API・データベース・分析ロジックで接続する。iPadの入力体験を保ちつつWindowsでも入力できる。
2. **オンラインを正本、端末は入力継続用の一時保存:** 同時編集や履歴の扱いを統一しやすい。試合会場の通信断に備え、入力イベントは端末側に保存し、復帰時に重複防止キーで同期する。衝突の自動解決はせず、同一試合を複数端末で編集した場合は履歴を残して解決画面を出す。
3. **191列をそのまま新DBにしない:** 新システムではチーム、選手、試合、出場登録、プレイ、投球、走者進塁など意味のまとまりで保存し、Excel列はインポート/エクスポート時に対応づける。
4. **計算ロジックをUIから分離:** 同じ定義をiOSとWebで使うため、主要集計はAPI/共通分析パッケージで計算する。端末側は入力操作と結果表示を担当する。
5. **一括移行せず、計算カテゴリごとに照合:** 基準データと既知の出力を固定し、旧マクロと新計算を比較してから移行対象を増やす。
6. **Excelは初期移行と外部共有の形式として残す:** 試合Excelの読込・出力を用意し、分析表や帳票も必要に応じてExcel/PDFで出す。日々の記録正本にはしない。

### Alternatives Considered

- **Excel VBAのまま改善:** 初期費用は小さいが、iPad・Windowsブラウザでの共通運用と保守性を解決しない。
- **Webアプリだけにする:** Windowsでは便利だが、試合中にiPadで使う入力体験、端末のオフライン保存、ホーム画面からの起動・端末機能連携で不利になる。後からネイティブアプリを足すとAPI設計が二重になる。
- **iOSアプリだけにする:** Windows側の入力要件を満たさない。
- **Excel VBAをコードへ自動変換:** フォーム、シート操作、状態管理、図表生成が絡むため、変換結果の保守性と正確さを担保しにくい。
- **Web技術でiOS/Windowsを単一UIにする:** 保守対象は減るが、入力中心のiPad画面やApple端末のオフライン挙動で要件を満たせるか、試作段階で評価する余地がある。SwiftUI案より開発速度・見た目・保守コストの総合比較をSpikeで行う。

### Open Questions (if any)

- **配布・利用範囲:** 滋賀大野球部専用で始めるか、将来複数チームが契約して使うサービスにするか。初期設計はteam_idによる分離を入れるが、決済やセルフ登録は初期版に含めない。
- **通信断の運用:** 1試合を複数端末から同時入力する必要があるか。初期推奨は1試合1端末入力、他端末は参照のみ。
- **分析機能の優先順位:** 61モジュール全てを同じ画面構成で再現するのか、実際に使う分析から移すのか。機能棚卸し後に利用頻度・意思決定への影響・検算可能性で決める。
- **帳票の再現度:** 表・グラフを画面に再現するだけか、現行の印刷/PDF様式も維持するか。主要帳票をサンプル化して決める。
- **クラウドと費用:** データ保管地域、認証方法、運用費上限、バックアップ保持期間はサービス選定前に決める。候補はPostgreSQLを正本にした一般的なクラウド構成とし、個人/チーム内部データを公開領域へ置かない。
- **過去データ移行:** 2020年以降の試合をどこまで取り込むか、またチーム内で誰が利用するかを決める。
- **iOS配布:** 個人利用のTestFlightから始めるか、App Store/組織配布にするかを決める。

## Step-by-Step Tasks

### Step 1: 既存資産を安全に固定する

元Excelを読み取り専用の基準として保管し、作業用コピーを作る。マクロ実行は原本上で行わない。ファイルの識別情報、シート一覧、VBA抽出結果のハッシュ、Excelバージョン、保管場所を非公開の作業記録に記す。選手名や生データをGitに入れない。

**Actions:**

- 2ブックのコピーを非公開の作業フォルダへ保管し、原本を変更しない。
- `olevba`で抽出した全モジュールを、実行せずに静的調査する。
- UserFormのコントロール名、表示文、選択肢、ボタン、イベントを一覧化する。
- 隠しシート、名前定義、列見出し、既存出力見本、外部参照を一覧化する。
- 基準試合データを選ぶ。少なくとも正常試合、延長/コールド等の特殊ケース、訂正を含むケースを含める。

**Files affected:**

- `~/Projects/baseball-analysis-platform/docs/spec/` 以下（別リポジトリ）
- 非公開ローカル作業記録

### Step 2: 機能カタログとデータ辞書を完成する

入力系と分析系を分けて、既存機能を漏れなく登録する。61分析モジュールは、モジュール名だけでなく入力条件・対象単位・指標・出力・依存列・作成シートを読む。24入力系モジュールは画面遷移と試合状態の更新を整理する。

**Actions:**

- 入力の流れを「チーム/大会→試合作成→メンバー→プレイ前状態→投球・プレイ→得点/走者更新→次プレイ→訂正/終了」で図示する。
- 191列それぞれの列名・意味・型・選択肢・必須条件・更新主体・正規モデル項目を対応づける。
- 主要オブジェクトをTeam、Season、Competition、Game、RosterEntry、Player、PlateAppearance、Pitch、Play、RunnerMovement、Substitutionとして定義する。列の実態に合わなければ確定前に調整する。
- 分析マクロを投手、打者、配球、打球方向、走塁/作戦、得失点、ケース/状況、出力/補助に分類する。
- 各集計で分子・分母、除外条件、欠損扱い、左右/カウント等の切り口を記録する。
- 機能をP0(試合入力の継続に必須)、P1(主要対策に必要)、P2(補助・特殊分析)に分類し、利用者と確認する。

**Files affected:**

**Actions:**

- iPadライブ入力画面のワイヤーフレームを作る。常時表示項目は回/表裏、スコア、SBO、打者、投手、塁状況とする。

- SwiftUIクライアント＋Webクライアント案と、共有Web UI案の2案を短いSpikeで比較する。
- API/DB候補を評価し、オフライン保存・同期、チーム分離、バックアップ、維持費、認証を含めて決定する。
- 操作テストをアナリストと記録担当者2名以上で行い、1打席に要する操作数・入力時間・誤入力の発生箇所を記録する。

### Step 6: MVPの試合入力を実装する

試合中に片手でも使える入力画面と、訂正・試合再開を含む入力状態遷移を作る。選択された一端末をその試合の入力担当とし、他端末からの同時更新は初期版では制限する。

**Actions:**

- 試合作成、先攻/後攻、メンバーと打順、スタメン/控え、投手を設定する。
- 回、表裏、スコア、SBO、アウト、走者、打者、投手、次打者を画面上に常時表示する。
- 投球を「球種、コース、球速、ボール/ストライク/ファウル、スイング/見逃し」の入力単位で記録する。
- 打席結果、打球種別/強度/位置、守備プレイ、失策、犠打、四死球、妨害、ボーク、牽制、盗塁、暴投/捕逸、交代、タイム等の現行ケースを網羅する。
- プレイ保存後に次の状態を自動提示し、ユーザーが状態を確定できるようにする。
- 直前訂正、任意プレイの編集、取消履歴、入力済み試合の再開を実装する。
- オフライン時は端末内にイベントを暗号化保存し、同期状況を明示する。再送しても重複を作らない。
- 入力を旧191列形式にエクスポートし、元マクロや滋賀大集計ツールで読み込めるか確認する。

- `apps/apple/`, `apps/web/`, `apps/api/`, `packages/domain/`（別リポジトリ）

### Step 8: 分析機能を段階的に移す

機能カタログの優先順位に従い、旧ブックの61分析モジュールをカテゴリごとに移す。各カテゴリで値と図の確認ができるまで次へ進まない。

**Actions:**

- Phase A: 打者/投手個人成績、打順別/イニング別/状況別成績。
- Phase B: 球種割合、カウント別/状況別配球、アウト別/打順別、1球前傾向。
- Phase C: 球種別コース別被打率、投球位置図、打球方向(個人/全体/左右投手別)。
- Phase D: 得点/失点パターン、ケース別攻撃/守備、牽制傾向、作戦分析、フィードバック。
- 各分析に期間、チーム、投手/打者、左右、カウント、走者状況のフィルタを必要範囲で提供する。
- 旧Excelとの一致率だけでなく、定義差・対象外・データ不足による差を説明できる画面を作る。
- HTMLの対策レポート、PowerPoint/PDF、打線一枚まとめへの出力は別の帳票要件として評価する。

- `packages/analysis/`, `apps/api/`, `apps/web/`, `apps/apple/`（別リポジトリ）

### Step 9: 限定運用と旧Excelからの切替

実試合で並行運用し、入力の速さ、欠損、誤入力、同期、分析結果を確認する。問題が落ち着くまでExcelを比較基準として残す。

**Actions:**

- 練習試合または過去試合の再入力でシナリオ受入を行う。
- まず1〜2試合を新旧並行記録し、1打席/1投球/全試合の入力差分を比較する。
- 通信断、アプリ終了、画面回転、選手交代、訂正、延長、再開、重複同期、複数チーム権限を確認する。
- 記録担当者から改善点を集めて入力画面を直す。
- 受入基準を満たした後に対象大会・チームを増やす。旧Excelは読み取り可能な移行保管とし、削除しない。

## Notes

- 計画上の技術候補は決定確定前の仮置き。Step 3のSpikeを経て、画面体験、オフライン、開発速度、保守性、運用費を比較してADRに記録する。
- マクロ抽出は静的な読み取りに限る。未確認のマクロを有効化して実行しない。
- 191列データの一部は1球、1プレイ、プレイ前後の状態が混在する。移行時は1行=1イベントと決めつけず、実データとの対応を確かめる。
- 自責点、失策、盗塁、走者進塁などは入力されていない情報から機械的に一意決定できない場合がある。旧VBAの挙動と現行滋賀大ツールの定義を別々に記録し、採用ルールを確認する。
- 複数チーム向けサービス化は将来の選択肢。初期の認証・team_id設計に備えるが、商用機能・決済・顧客管理は要求に含めない。
